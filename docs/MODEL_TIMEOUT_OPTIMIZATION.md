# 模型超时与进度优化（2026-09-06）

实际故障：本机迁移配置保留了 `LLM_TIMEOUT=60`、`PLANNER_REQUEST_TIMEOUT=90`，SDK 默认另有 2 次重试。模型首次请求后触发 SDK 重试，整趟规划随后被 90 秒的外层预算取消，检查点停留在生成节点之前。点击继续会重新执行该节点，不能续接远端模型已经生成的半截输出。

## 已生效的配置

```dotenv
LLM_TIMEOUT=180
LLM_MAX_RETRIES=0
LLM_STREAMING=true
LLM_PROGRESS_INTERVAL=10
PLANNER_REQUEST_TIMEOUT=600
PLANNER_MAX_ATTEMPTS=3
PLANNER_ENABLE_RERANK=false
```

`LLM_TIMEOUT` 同时用于模型客户端超时参数，以及每次模型策略调用的异步总时限。即使远端持续发送心跳或 SDK 配置了内部重试，单次策略调用也受这个总时限约束。整趟 600 秒预算包含工具采集、模型调用、解析与校验。3 次 180 秒调用之外留出约 60 秒；它是时间预算，不保证远端服务成功。结构化策略兼容回退或缓慢工具仍可能用尽整体预算，届时会明确显示整趟超时。

默认关闭 SDK 内部重试，由 LangGraph 的候选重试提供可见原因和次数。模型客户端声明支持 `streaming` 时才设置该属性；未声明的供应商保留原调用方式，仍可展示等待心跳。供应商专有选项继续通过 `LLM_MODEL_KWARGS` 配置，手动覆盖的选项优先。

本机私有配置位于 `~/dev/config/trip-backend.env`，旧配置备份为同目录下 `trip-backend.env.before-timeout-optimization-20260906`。这两个文件均不进入 Git。修改配置后需重启后端。

## 用户能看到的变化

- 调用开始：日志记录输入字符数、输出上限、单次超时、SDK 重试次数。
- 每 10 秒等待状态：明确表示尚在等待完整响应，不假装模型已生成答案。
- 支持流式的模型：首次收到响应、后续最多每 2 秒显示接收进度和行程正文字符数。最终仍等待完整 JSON 并执行原有校验。
- 接口超时、连接失败、服务限流、认证错误分别记录错误码、异常类型链和可用的 HTTP 状态，不记录错误响应正文。
- 整体超时会注明 600 秒任务上限；取消时记录模型中断和耗时，并取消本地请求协程。
- 供应商可能仍在处理已发送的请求，本地取消不保证远端停止计费。
- 页面主进度区域直接显示最新模型状态，不必展开执行记录。

进度事件只包含计数与状态，不包含提示词、生成的 JSON 片段或内部思考内容。SSE 重放、登录 Cookie、历史行程和检查点恢复方式保持兼容。

## 提示词精简

删除与系统提示重复的长规则；候选景点跨检索分类重复时只保留一次。不同价格、地址、位置等变体仍保留，餐饮候选及忌口、天气、用户要求和预算约束不裁掉。去掉已有规范价格提示时重复的原始价格、检索关键词等元数据。原始工具快照保留用于校验和恢复。

对本次失败的 4 天行程，系统提示加用户输入从 **49,625 字符降为 37,309 字符（减少 24.8%）**。这是字符数，不等于 token 数或耗时同比下降。输出上限保持原值，避免通过减小上限导致 JSON 截断；要求描述简短且不省略必需字段。

生成节点从已保存的原始上下文重建输入，因此旧失败行程点击继续也能使用新压缩逻辑，无需重新调用地图服务。

## 在 VS Code 中单独重启后端

确认没有仍需运行的规划任务，在开发容器终端执行：

```bash
python /workspace/scripts/stop_services.py --only backend
cd /workspace/backend
uv run --locked python run.py
```

也可以在停止后重新运行 VS Code 的“启动后端（含日志）”任务。前端使用热更新，刷新浏览器即可。
