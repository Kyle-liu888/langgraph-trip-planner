# 项目讲解与面试准备

适用方向：大模型应用 / Agent 开发。本文是基于当前代码的讲解提纲，不是对个人经历或生产规模的背书。请用你能解释、能复现的部分回答问题；项目基于开源旅行助手示例重构，不宣称从零训练了模型。

## 一分钟介绍

> 这是一个基于 LangGraph 的单城旅行规划应用。用户填写城市、日期和出行偏好后，后端先获取景点、酒店、餐厅与天气候选，再调用可切换供应商的模型生成结构化行程。程序会校验结果，必要时重试或返回带提示的兜底方案。用户可以实时看执行进度，并在自己的账号下保存、编辑、导出行程；运行中断后可以从持久化检查点手动恢复。
>
> 重点不是让模型多说几段旅行建议，而是把一次模型调用做成有状态、可观察、可校验的应用流程。目前部署在一台阿里云 ECS 上，用三个常驻容器提供个人入口、旅行应用与独立 PostgreSQL，已通过公网注册、真实模型生成和地图显示验收。规划任务仍在单后端进程内运行，没有宣称分布式调度或多机高可用。

## 从一次点击讲清完整流程

```text
填写需求 → POST /api/trips
              │ Cookie + CSRF + 幂等键 + 额度/活跃任务检查
              ▼
          保存业务记录并返回 202 + 行程 ID
              │
              ├─ 浏览器订阅 SSE，显示真实节点与模型接收状态
              ▼
          后台 RunManager（单进程任务）
              │
 collect_context → build_prompt → generate_candidate → validate_candidate
                                          ▲                  │
                                          └── 条件重试 ───────┤
                                  合法候选 → select_best_candidate
                                  达到上限且无合法候选 → create_fallback
              │
              ▼
          保存最终行程；节点状态另由 PostgreSQL Checkpointer 保存
              │
              ▼
          结果页加载地图、图片、开放参考信息与官方/攻略入口
```

认证、任务管理和图执行不是一回事；SSE 只是进度传输，不负责驱动模型。景点图片和开放信息是结果展示增强，不加入模型上下文，也不参与当前排序。

## 关键设计、收益和取舍

| 设计 | 解决的问题 | 必须说明的边界 |
| --- | --- | --- |
| LangChain 模型网关 | 隔离模型供应商，统一调用接口 | 新供应商仍需安装集成、配置认证并实测，不保证所有能力相同 |
| LangGraph 显式节点和条件边 | 清晰组织采集、生成、校验、重试与兜底 | 图结构本身不保证模型内容正确 |
| Pydantic + 业务规则校验 | 约束 JSON 结构、日期和候选地点使用等 | 不能把通过程序校验等同于景区当天真的开放 |
| 事件先入库，再由 SSE 推送 | 离开页面后仍可查看执行记录，断线可重放 | 不展示模型私有思考；重复收到事件需去重 |
| 业务记录 + Checkpointer | 历史可编辑，流程可按节点恢复 | 不是逐字符续写；被中断的外部调用可能重跑和再次计费 |
| 幂等键 + 版本号 revision | 减少重复提交，防止旧编辑覆盖新结果 | 不等于外部 API 的 exactly-once 保证 |
| 自建账号与会话 Cookie | 不依赖远程登录服务，账号与数据保存在自己的数据库 | 邮箱仅作标识，没有邮件验证、找回密码邮件或 GitHub 登录 |
| 本地开发容器 + 生产 Compose | 隔离依赖，生产数据库独立于开发数据 | 单机仍有故障单点；已执行手动备份，尚无定时异地备份 |

业务数据库应用账号不是 PostgreSQL 超级用户；但业务表 owner 可以绕过 RLS，所以用户行程隔离的关键仍是后端在查询中同时约束行程 ID 和已认证用户 ID，不能把 RLS 当成已经独立完成了全部隔离。

## 常见追问

### 为什么不直接让模型生成一篇攻略？

自由文本不适合可靠地绘制地图、计算预算、编辑保存和做字段校验。项目使用候选数据和统一 TripPlan 结构，让结果能被程序消费。候选数据和模型都仍可能有错误，需要显示来源和限制。

### LangGraph 中有多少个 Agent？

当前主要是一个显式工作流，不应把每个函数节点都包装成一个自主 Agent，也不应宣传成多个角色自由协商。用源码中的节点职责解释更准确。

### 项目有没有后训练？是不是本地大模型？

没有训练、LoRA 或训练权重。当前主流程是调用配置的模型服务做在线推理；开发环境、数据库在本地，不代表模型也在本机运行。

### 如何处理模型超时或输出不完整？

区分单次调用超时、整体任务超时、结构化能力不兼容和业务校验失败。通过上下文压缩、结构化策略选择、进度事件和有限重试减少盲等。最终状态明确区分 completed、fallback、failed 和 interrupted，不把兜底当成正常模型成功。

相关实现见 `backend/app/llm/`、`backend/app/graph/nodes.py`，历史问题分析见 [模型超时优化](MODEL_TIMEOUT_OPTIMIZATION.md) 与 [响应处理修复](MODEL_RESPONSE_FIX.md)。

### 刷新页面会不会重新扣模型调用次数？

刷新历史页面、重订阅 SSE 不会重新提交规划任务。用户点击“从检查点继续规划”则可能再次执行被中断的模型调用，供应商可能再次计费。已有幂等处理并不意味着网络服务绝不会重复执行。

### 门票和开放时间是否实时准确？

不是实时票务系统。门票是预算估算；高德开放时间属于参考；已登记景点的官方预约/价格链接供用户核验，不查询余票或自动预约。今日时间不冒充未来日期安排，目前也没有自动回避闭馆日期。

### 大众点评按钮是否已经找到了该景点攻略？

没有。按钮打开大众点评官网，用户复制“城市＋景点＋游玩攻略”自行查询。小红书使用已验证格式的搜索入口。项目不抓取或审核平台内容，也不保证免登录或免验证码。

### 为什么说四个模块，实际只有三个容器？

前端、API、规划 Worker、数据库是逻辑分工。目前 Caddy 和静态前端共用 web 容器；API 与 RunManager 规划任务共用 backend 容器；PostgreSQL 独立运行。migrate 是一次性任务，不常驻。这个取舍适合单机作品集，维护步骤少，但 API 与任务生命周期耦合。

### 有高可用吗？能直接横向扩容吗？

有健康检查、进程自动重启、持久化检查点和手动备份，属于可恢复性；没有多机高可用。ECS 和数据库仍是单点，单个后端持有数据库会话锁，不能直接增加副本。后续先拆独立任务队列和 Worker，设计租约、重复执行处理与任务接管，再做数据库容灾和负载均衡。

### 上线遇到了什么真实问题？

一是服务器内页面正常但公网无法访问，最终定位为阿里云安全组未放行 TCP 80。二是本机 localhost 可以使用的 `crypto.randomUUID()` 在 HTTP 公网 IP 上不可用，导致浏览器无法提交行程；增加 `getRandomValues` 的 UUID v4 兼容实现后，用公网浏览器重新完成注册、生成、结果和地图验收。这说明 API 测试通过不代表真实浏览器路径已通过。

### 如何证明系统能运行？

现场可以演示登录、历史行程、日期导航、编辑和规划记录；自动化测试用模拟模型与地图覆盖分支。浏览器验收另有隔离服务，不使用用户数据和真实模型额度。真实 PostgreSQL 验收是单独的 opt-in 测试，不能拿 SQLite 或内存 Checkpointer 的测试代替。

可直接从[个人入口](http://8.163.48.116/)进入旅行项目。当前记录与复现方式见[云部署验收](CLOUD_DEPLOYMENT.md#已验证与未验证)、[浏览器验收](BROWSER_ACCEPTANCE.md)、[本地操作手册](LOCAL_DEV_GUIDE.md)。未运行过的负载、生产故障恢复或供应商兼容测试，不应说成已验证。

## 演示顺序

1. 打开已保存行程，展示历史与完成状态，不先触发收费规划。
2. 展开“查看规划记录”，解释采集、模型生成、校验和完成事件。
3. 展示日期导航、地图与带来源的景点信息，指出数据边界。
4. 在测试行程上演示编辑保存，说明 revision 冲突保护。
5. 打开 [架构设计](ARCHITECTURE.md) 和 [模块索引](../PROJECT_STRUCTURE.md)，把界面行为对应到代码。
6. 说明已知不足和下一步验证计划，不用未经测量的性能数字。

## 当前限制与可继续改进的方向

- 单城规划、单后端进程；不是分布式任务队列或多租户生产平台。
- 供应商和高德的联网、权限、费用会影响体验；usage 元数据不是完整累计账单。
- 官方来源覆盖有限，尚未自动校验闭馆冲突或实时余票。
- 错误处理、单元测试和浏览器验收已有基础，已完成单机部署及部分恢复验证，性能压测、整机重启和多机灾难恢复仍需独立验证。
- 未来可讨论共享任务队列、模型成本统计、更完整的浏览器自动化、官方来源扩展；这些是方向，不是已完成功能。
