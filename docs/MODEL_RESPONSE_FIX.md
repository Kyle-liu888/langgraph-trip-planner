# 持续零正文与目的地校验失败修复（2026-09-06）

## 故障证据

行程 `62ecf9c8-f07a-4807-b1f1-2a84915666f5` 的前两次模型调用在 180 秒时超时。第三次约 80 秒后才开始出现正文，93.5 秒完成。返回用量包含 8,604 个 reasoning tokens，说明此前的流式响应主要处于推理阶段，不是网络完全无响应。

随后业务校验失败：请求目的地为“云南”，模型返回“昆明”。原始候选资料同时包含昆明、大理、丽江等多个城市。当前规划规则采用单城、连续入住同一家酒店的设计，不能把省份输入默认为省会，也不能直接把返回地名改成省名来掩盖问题。

## 根因与修复

1. 本机 `LLM_THINKING_MODE` 未配置，读取为 `auto`。[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/thinking_mode/)中 V4 默认开启思考。当前私有配置和示例显式设为 `disabled`。
2. 更关键的是，`with_structured_output(include_raw=True)` 返回的组合链包含 `RunnableMap`；从最外层 `ainvoke` 传入的参数没有传给嵌套模型。原来生成节点设置的 `thinking`、输出 token 上限和温度未真正进入 HTTP 请求。现在在构建结构化输出链时绑定这些参数，纯提示词回退路径继续直接传给模型。无法接受这些参数的结构化适配器会走已有的兼容回退机制。
3. 进度回调区分等待、推理、正文三个阶段。只根据收到的响应字段判断阶段，不展示或记录思考内容。支持字符串及分块正文计数。
4. 前后端在创建任务前提示省份/自治区输入需改成具体城市，不创建任务、不消耗每日配额。旧失败任务恢复也执行同样检查；历史记录和已有结果不修改。
5. 提示词明确要求顶层 city 逐字复制用户输入；压缩候选保留来源城市。目的地校验错误增加 `DESTINATION_MISMATCH` 错误码和中文提示，不再只显示 `ValueError`。

前后端省份判定只是防止明确过宽的输入，不是完整地理编码服务；任意错别字、多城市自由文本等仍需后续单独设计目的地选择器。模型输出仍须通过原有校验，未降低校验要求。

## 验证与使用

- 后端 41 项测试通过，默认跳过 1 项需真实 PostgreSQL 配置的验收。
- 前端 20 项测试通过，类型检查和生产构建通过。
- 通过真实 LangGraph 节点、ChatDeepSeek 适配器和模拟 HTTP 服务，直接断言请求包含 `thinking.type=disabled`、输出上限及温度，结构化结果完整返回。
- 覆盖推理阶段不泄露内容、分块正文计数、省份输入不消耗配额、地名不一致的可见校验原因等回归测试。
- 本轮未自动调用真实模型 API。刷新页面并新建行程，填写“昆明”或“丽江”等具体目的地，由用户主动提交真实规划。

之前保存的兜底行程不会自动转换成模型生成结果；当前需新建具体城市行程。省级跨城市规划涉及城际交通、住宿切换和多地天气，需要作为独立功能实现。
